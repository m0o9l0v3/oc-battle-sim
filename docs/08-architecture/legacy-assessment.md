## 1. 概要

前回の体験アプリ `oc26-stage`（中学生向け「ステージ改造」）の資産を、本プロジェクト（`oc-battle-sim`）で再利用できるかを評価する。system-overview.md §9 の方針どおり、**無条件には流用せず**、資産ごとに次の4区分で判定する。

| 判定 | 意味 |
|---|---|
| **Reuse** | ほぼそのまま使う |
| **Refactor** | 考え方・構造・コードの一部を使うが、本プロジェクトの要件に合わせて作り直す |
| **Replace** | 要件が異なるため、新規に作る。旧実装は参考にとどめる |
| **Discard** | 使わない |

### 2.1 oc26-stage の性格（再利用の前提）

`oc26-stage` は、本プロジェクトとは次の点で**設計前提が異なる**。評価はこの差を前提にしている。

| 観点 | oc26-stage | oc-battle-sim |
|---|---|---|
| 体験 | 1人用。ステージを作って自分でクリアする | 1対1の対戦。能力値設計→対戦→Report→再戦 |
| 配信 | `file://` でも動く単一HTML。サーバーなし | GitHub Pages（会期後の持ち帰り用QRの接続先）+ 別ホストの WebSocket バックエンド。当日の配信方法は #66 で決める |
| 実行時依存 | ゼロ（AGENTS.md 3.1） | 制約なし（React, Vite 等を使う） |
| 言語 | JavaScript | TypeScript |
| ステージの意味 | ゴールに到達する | 場外に吹き飛ばして撃墜する。対戦成立のための検証が必要 |

そのため、`oc26-stage` の AGENTS.md の規約（外部依存ゼロ、単一HTML、`file://` 動作、エラー非表示方針など）は、**本プロジェクトには持ち込まない**。

以降、判定の理由を、再利用するもの（Reuse / Refactor）を中心に述べる。

### 3.2 Canvas 描画（ステージ）— Refactor

- **使えるもの:** `drawGrid` / `drawStageCell` のセル描画、`canvasCellFromEvent`（ポインタ座標→セル番号）、色を `config.colors` に集約している点。
- **直すもの:**
  - `ctx` と `config` をグローバルなアプリ状態から受け取る構造のため、`engine` の描画インターフェースとして引数で渡す形に整理する。
  - セル種別（敵・ゴール・トゲなど）が描画関数に直書きされている。本プロジェクトのセル種別に合わせて作り直す。
  - 描画対象の座標が `cellSize = 48` 固定。画面サイズへのスケーリング（#20）を別途用意する。
- **改修量:** 小〜中。

### 3.3 Canvas 描画（キャラクター）— Replace

プレイヤーと敵は単純な図形で描かれており、REQ-FTR-03（図形の貼り合わせを避ける）と NFR-05 を満たさない。パーツ合成レンダラー（#29）を新規に作る。旧コードに流用する部分はない。

### 3.4 ゲームループ — Refactor

- **使えるもの:** 固定ステップ（`stepHz: 60`）の時間積算方式と、1フレームあたりの最大ステップ数の上限（`maxStepsPerFrame: 5`）。高リフレッシュレートの画面でも物理速度が変わらず、遅い端末でも処理が暴走しない。NFR-03 の方針と合致する。
- **直すもの:** ループが `createPlayController` のクロージャの中にあり、`requestAnimationFrame`・入力・描画・ゲーム状態が一体になっている。`engine` に「更新と描画が分離された」ループとして切り出す（#20）。ゲームロジックを描画・通信から独立させる方針（#17）に反する構造は引き継がない。
- **改修量:** 中。

### 3.5 衝突判定・物理 — Refactor（敵挙動などは Discard）

- **使えるもの:**
  - `moveX` / `moveY` に分離した軸分離 AABB のタイル衝突。左右・上下を個別にテストできる設計。
  - 重力、落下速度の上限、着地判定（`onGround`）。
  - DOM に依存しない純粋関数で、`test/physics.test.js`（約290行）が付いている。
- **直すもの:**
  - パラメータを `config.physics`（グローバルな単一の値）から読んでいる。ファイターごとに `speed` / `jumpPower` が違うため、物体ごとのパラメータを引数で渡す形にする（#22）。
  - 対戦に必要な機能が無い: 物体どうしの攻撃判定、ダメージ蓄積に応じた吹き飛ばし、場外判定、足場のすり抜け有無。これらは新規（#23, #24）。
  - 衝突対象がグリッドのみで、固体セルの種類が配列で固定されている。
- **改修量:** 中。ただしタイル衝突の核は小さく、移植は容易。

### 3.6 敵・トゲ・ジャンプ台・落ちるブロック・壁キック — Discard

どれも1人用ステージ攻略のためのギミックで、対戦の MVP 範囲外（system-overview.md §7.1「複雑なコンボシステム、アイテム…」）。コードは引き継がない。なお壁キックの「同じ壁を連続で蹴れない」判定など、操作感の調整ノウハウは、将来の復帰仕様（#12）を検討するときの参考にできる。

### 3.7 ステージデータとグリッドエディタ — Refactor

- **ステージデータ（`stage.js`）:** セルを数値で持つ二次元配列、`cloneGrid`、左右端の列を編集不可にする `lockedCols`、開始セルの保護といった**編集可否の考え方**を流用できる。DOM 非依存でテスト可能（`stage.test.js`）。ただしセル種別（敵・ゴール・トゲ…）は別物で、対戦用には「足場」「スポーン位置」「場外領域」などが必要。ゴールが1つだけという制約は、スポーン2つなどに置き換わる（#13, #31）。
- **エディタ（`edit.js`）:** 「押した先が選択中の種別と同じなら、そのドラッグ全体を消去にする。違えば配置にする」「1ストロークで同じセルは1回だけ処理する」という操作ルールは、置いたそばから消える往復を防ぐ良い設計。**そのまま引き継ぐ価値が高い**（#14, #33）。
- **直すもの:** `app` オブジェクト（状態・計測・進行管理）への依存を外し、React のコンポーネントと切り離したロジックにする。
- **改修量:** 中。

### 3.8 URLフラグメント共有 — Refactor

- **使えるもの:** `<名前のBase64URL>.<色>.<RLE圧縮グリッド>` の形式。連長を英字に置き換える RLE 圧縮は、20×12 のグリッドを短い文字列にできる。復元関数 `decodeStage` が**例外を投げない**設計と、`share-url.js` が `location` を参照せず、固定の公開URLから共有URLを組み立てる点（会場LANのIPをQRに焼き込まない）は、そのまま踏襲する価値がある。
- **直すもの:**
  - 旧版の HSL 色相形式との互換コード（`legacyHueToHex3`）は不要。破棄する。
  - 形式にバージョン番号を持たせ、本プロジェクトの StageData / CharacterConfig（#18）に合わせて作り直す。
  - 復元に失敗したとき**黙って初期ステージに戻す**方針は、oc26-stage 固有のもの（AGENTS.md 3.5）。本プロジェクトのステージ検証（#13）はエラー内容を参加者に示すため、そのまま採用しない。URL 復元部分だけ「失敗したら null を返し、呼び出し側が決める」形に整理する。
- **改修量:** 小〜中。

### 3.9 QRコード生成 — Reuse

- **使えるもの:** `vendor/qrcodegen.js`（Project Nayuki の QR コード生成ライブラリ、MIT）。Reed-Solomon 符号を含み、外部依存がない。ルーム参加用 URL の QR 表示（#45）にそのまま使える。`share.js` の Canvas への描画コード（モジュールサイズ・クワイエットゾーンの扱い）も参考になる。
- **注意（§5）:** ライブラリ本体の表記と同梱ライセンス文の著作権者が一致していない。
- **移植方法:** npm の `qrcode-generator` 等を使う選択肢もあるが、このライブラリは小さく、検証済みのためそのまま同梱し、TypeScript の型宣言だけ追加する案が最も手間が少ない。採否は #45 で決める。

### 3.10 モバイル入力 — Refactor

- **使えるもの:** `touchLeft` / `touchRight` / ジャンプの入力フラグ、`pointerdown` を使ったタッチ入力、端末種別を判定して画面を切り替える仕組み（`device-mobile`）。
- **足りないもの:** 本プロジェクトは横持ち前提の仮想コントローラー、移動と攻撃の同時入力（マルチタッチ）、ダブルタップズームやスクロールの抑止を必要とする（#48, #49）。さらに、入力を「キーボード / 仮想パッド / ネットワーク」で差し替えられる抽象化レイヤ（#21）が必要で、旧実装は `play.js` 内の入力フラグに直結している。
- **改修量:** 大。再利用できるのは着想が中心。

### 3.11 UI・画面文言・設定の集約 — Replace / Refactor

- 画面は単一HTMLテンプレートと CSS（約850行）で、画面構成が「ステージ改造」専用。React 前提の本プロジェクトとは構造が合わないため、**Replace**（#36）。
- 画面文言を直接コードに埋め込まず、`config.js` に集約する方針は、次回以降の調整が楽になるため**踏襲**する（`CONFIG` は Refactor）。ただし値は全面的に入れ替える。

### 3.12 計測 — Discard

`metrics.js` は操作回数などを localStorage に残す仕組み。Battle Report（#37）は対戦中のイベントから指標を作るもので、目的が異なる。ただし「localStorage が使えない環境でも体験を止めない」という try/catch の作法は参考にする。

### 3.13 進行管理システム — Refactor

親機 PC の Node.js 標準 HTTP サーバーで進行フェーズ（準備→制作→仕上げ→共有→…）を管理し、各操作の可否を切り替える仕組み。本プロジェクトの当日運営（#7）の設計で**参考にする**が、実装は流用しない。

- 判定の見直し（2026-10-04）: 会場の有線LANがインターネットに出られないことが分かり、当日の配信・進行管理・通信は親機PCのローカルサーバーが担当することになった（[event-connection.md](./event-connection.md)）。これは `oc26-stage` の親機サーバーと同じ構成のため、判定を Replace から Refactor に変更する。
- 流用できる点: 静的ファイルの配信、フェーズごとの操作可否、親機と通信できなくても体験を止めない縮退動作、スタッフ向け管理画面。改修量は、中。
- 直す点: 参加者データを保存・受信しない方針は踏襲する。再戦の受付制御、TypeScript への移植が必要（#67、#68）。

### 3.14 ビルド・CI — Discard

`tools/build.mjs` は import を辿って単一 HTML に結合する自作ビルダー、`.gitlab-ci.yml` は GitLab Pages 向け。本プロジェクトは Vite + GitHub Actions（#2, #3）に移行済みで、不要。

### 3.15 テスト — Refactor

18ファイル・160件、現状はすべて合格（調査時に実行確認）。`physics.test.js`、`codec.test.js`、`stage.test.js` は、移植元の仕様確認として価値がある。`node:test` から Vitest + TypeScript へ書き換えて、対応する資産と一緒に移す。

### 3.16 印刷・コード体験 — Discard（印刷は持ち帰り機能の要否次第で見直し）

- **印刷機能（持ち帰りカード）、DEMO（色コード体験）:** 対戦アプリの要件にない。

### 3.17 学校ロゴ・ブランディング — Refactor

- 学校から許可を得て公式に提供されたロゴであり、使用できる。
- **直すもの:** `oc26-stage` では SVG を Base64 にして HTML に直接埋め込んでいる。本プロジェクトでは、公式提供のファイルを `src/assets/` に置き、画像として読み込む。ヘッダーの高さ・最大幅・リンク先を設定に集約する方針（`config.branding`）は踏襲する。
- **許可の範囲（所有者より確認）:** 使用はオープンキャンパスでの使用に限る。それ以外に特別な制限はない。
- **主な用途:** イベント終了後に配布する、ステージ読み込み用の QR コードを発行するときに、学校の出典であることを参加者に伝えるために使う。
- **記録すること:** 上記の許可の範囲と提供元を、権利確認（#50）にも記録する。オープンキャンパス以外の場面（公開 Web サイトの常設表示など）で使う場合は、あらためて学校に確認する。
- **要件との関係:** この用途は、system-overview.md に書かれていない「持ち帰り用 QR コード」を前提にしている（§7）。
- **表示するか:** 表示位置・要否は UI 設計（#15, #36）で決める。本プロジェクトに必須の要素ではない。
