## 1. 概要

何を、どの方法で、いつ確認するかを定める。確認の手段は、次の4つに分ける。

| 区分 | 記号 | 何で確認するか | 実行する場面 |
|---|---|---|---|
| 自動テスト（ユニット） | **U** | Vitest。DOM なし（Node） | PR のたび（CI） |
| 自動テスト（コンポーネント・結合） | **C** | Vitest + jsdom（Testing Library）。画面フロー、入力ソース、ゲームループ | PR のたび（CI） |
| 手動テスト | **M** | 人が、実際のブラウザで確認する。チェック項目で記録 | マイルストーンごと、リハーサル |
| 実機・性能検証 | **P** | 会場想定のPC・スマホで、FPS・操作感・負荷を計測 | M4（#51）、リリース前 |

当日の運用（設営・起動・リセットの手順）の点検は、別文書の `event-checklist.md`（#52）で扱う。本書は、**アプリが仕様どおりに動くか**を確認する計画である。

## 2. 目的

- 各分野の Acceptance Criteria の**すべて**に、確認の手段を割り当てる（§6）。
- ゲームロジックを自動テストで守り、仕様の数値（式・係数）の変更が、意図せず結果を変えないようにする。
- 60 FPS と、操作の遅延のなさを、会場想定の端末で、決まった方法で測る（§7）。
- 当日に起こりうる障害（親機の停止、通信の切断、キーボードの同時押し）を、事前に確認する。

## 4. テストの方針

1. **ゲームロジックは、自動テストで守る。** [frontend.md](../08-architecture/frontend.md) の core 層（physics / combat / fighter / stage / battle / report / share / cpu）は、DOM・時計・乱数に依存しないため、Node 上でテストできる。仕様書の「計算の例」を、そのまま期待値にする。
2. **試合全体は、リプレイテストで守る。** 入力の列（`ReplaySource`）から、最終状態とイベント列を、期待値と比べる（決定性の確認）。
3. **画面は、操作の流れで守る。** 状態遷移（S01〜S12）と、データの保持・破棄を、コンポーネントテストで確認する。見た目の細部は、手動で確認する。
4. **見た目・体感・性能は、人と実機で確認する。** 自動化の費用に見合わないもの（キャラクターの見た目、操作感、60 FPS）は、チェック項目と計測手順を決めて確認する。
5. **仕様の変更は、テストも変える。** 式・係数・数値の変更（#25 の調整を含む）では、変更の理由を残して、期待値を更新する。期待値だけを、結果に合わせて黙って書き換えない。
6. **失敗は、Issue にする。** 発見した不具合は、再現手順とともに Issue 化する（#51）。

### 5.2 コンポーネント・結合テスト（C）

Vitest + jsdom。画面は、Testing Library で操作する。

| 対象 | 確認すること |
|---|---|
| 画面フローの reducer | S01〜S12 の遷移表。戻れる画面・戻れない画面（S07・S10・S08）。S09 の完了条件（1P の能力値が1つ以上変わっている、1P・2P とも合計20）。S11 に進める条件（2戦以上） |
| セッションストア・保存 | 保存のタイミング、更新（再開）で復元、S07・S10 から S06 に戻る、S12 の保持、`?reset` の消費（URL から取り除く）、一斉リセット（`sessionId` の変化）、`sessionId: null` の扱い、壊れた保存・版違いは全体を捨てる、`localStorage` が使えないときも動く、容量超過時の縮小（data-model.md §6、§9） |
| `KeyboardSource` | `KeyboardEvent.code`での判定（1P・2P・テンキーなしの2P）、`keydown` のラッチ（次のステップまで保持）、`event.repeat` の無視、左右の「押したことがある」判定、`preventDefault`（対戦キーのみ） |
| ゲームループ | 時刻と `requestAnimationFrame` を差し替え、固定ステップの積算、1フレーム最大5ステップ、非表示からの復帰で時間をまとめて進めない、`stop()` の後始末、例外時に停止して安全な画面へ |
| `HostLink`（偽の実装） | 通信失敗でも対戦が続く（`MatchRunner` が `HostLink` に依存しない）、10秒の通信不能で操作がすべて許可（フェイルオープン）、回復後に最新状態へ追従、`sessionId` 変化で破棄、新しく始める操作のみ制限され、進行中の対戦は止まらない |
| 画面ごとの主要操作 | S02（外観・名前、個人情報の注意書き）、S03（ポイント配分、残りポイントの表示と理由）、S04（プリセットだけで進める、エディタの検証エラー表示）、S06（キー確認）、S08・S11（指標と比較の表示、「正解を示さない」ことばの規則）、S12（QR と URL の表示） |
| 持ち帰りの復元 | 正常な復元、失敗時に理由と次の操作が表示される、失敗を隠して標準設定を「復元できた」ように見せない（character-config.md §5.4） |
| 文言 | 設定ファイルにある文言だけを使い、コードに直接書かれていない（検査は、lint または文言の一覧との突き合わせ） |

### 5.3 コードの規約の検査（U / lint）

| 検査 | 方法 |
|---|---|
| core が、react・DOM・時計・乱数・通信を使わない（frontend.md §4.3 D1〜D3） | ESLint の `no-restricted-imports`、`no-restricted-globals`（core のディレクトリに限定）。CI で失敗させる |
| 外部の資源を読まない（フォント・画像・スクリプト。ui-design.md §10） | ビルド成果物（`dist`）の中を調べるスクリプト（`http://`、`https://` の外部参照が、許可リスト以外にないこと）。CI で失敗させる |
| 型チェック・フォーマット | `tsc -b`、`eslint`、`prettier --check`（既存の CI） |

### 5.4 結合・障害の試験（M、会場に近い環境）

親機のローカルサーバーと参加者PCを、実際のLANでつないで確認する。

| # | 試験 | 確認すること | 参照 |
|---|---|---|---|
| T1 | 一斉リセット | 20台すべてで S01 に戻る。対戦中の台も戻る。データ（設定・ステージ・戦の記録）が残らない | event-control.md §9 |
| T2 | 個別リセット（`/?reset`） | 1台だけ S01 に戻る。**そのあとの通常の更新（F5）で、新しく作った設定が消えない**（URL から `reset` が取り除かれている） | data-model.md §6.4 |
| T3 | 更新（再開） | S05・S08・S11・S12 で更新すると、同じ画面・同じ設定に戻る。対戦中に更新すると S06 に戻る。S04 の編集中のステージが残る | user-flow.md §6.1.1 |
| T4 | 親機の停止 | 停止している間も、対戦・設定が続けられる。10秒後に操作の制限がなくなる。**ブラウザを更新しない**。親機の復旧後、最新の進行状態に追従する | event-control.md §10 |
| T5 | LANケーブルを抜く | T4 と同じ。復旧後、`sessionId` が変わっていれば自動で S01 に戻る（前の参加者のデータが残らない） | event-control.md §9.4 |
| T6 | フェーズの変更 | 進行中の対戦は中断されない。新しい操作（再戦、設定変更）だけが、フェーズに従って許可・不許可になる。理由が表示される | event-control.md §5.3、§6 |
| T7 | 再戦の受付停止 | 受付停止中は、新しい再戦を始められない。進行中の対戦は続く | event-control.md §6.3 |
| T8 | ターンの入れ替え | 20台が S01 に戻り、前の参加者の名前・作品が見えない（画面確認ソフトで確認） | event-operation.md §6.5 |
| T9 | キーボードの同時押し | 1P（A D W F）と2P（テンキー 4 6 8 5、および ← → ↑ /）を同時に押し続けても、入力が落ちない。落ちるキーの組み合わせがあれば、配置を見直す | pc-ui.md §7、event-connection.md §6 |
| T10 | 持ち帰りQRの往復 | S12 のQRを、スマホで読み取り、GitHub Pages で開く。PC で設定が復元される。QRを読み取れないとき、URL の文字で開ける | scope.md（M2 の完了条件） |

## 7. 性能・端末の検証（P）

### 7.1 対象端末

| 区分 | 対象 | 目的 | 合格基準の区分 |
|---|---|---|---|
| **会場想定PC** | **当日の会場のPC（参加者PC 20台のうち、少なくとも、最も古い・性能が低いと想定される1台）。親機PC** | 60 FPS の維持。NFR-03 の主な確認対象 | 必須 |
| 参考PC | 開発に使うPC | 開発中の確認 | 参考値 |
| **低性能スマートフォン**（目標機能。M3） | iOS Safari の古めの機種、Android Chrome の低価格機（入手できるもの） | NFR-03、NFR-04（低性能スマホの考慮）。持ち帰り後の体験 | 目標 |

- 会場のPCの、機種・CPU・メモリ・OS・ブラウザの名前とバージョン・画面の解像度を、**#51 の最初の作業として記録する**。記録がなければ、本書のこの表を更新する。
- スマホの機種は、入手できる範囲で、#51 で決める。**スマホ単体プレイ（M3）が実装されるまでは、スマホの性能検証は不要**（MVP では、スマホは案内と復元した設定の表示のみ。frontend.md §10）。

### 7.2 60 FPS の計測方法

| 項目 | 内容 |
|---|---|
| 計測の対象 | 対戦中（S05、S07、S10）の、描画のフレーム間隔と、1ステップの処理時間 |
| 計測の仕組み | 開発用の計測（フレームの間隔を、`requestAnimationFrame` の時刻で記録）。**本番のビルドには含めない**（URL の `?perf` で有効にするなど、通常は無効）。結果は、画面の隅の表示と、`console` へのまとめの出力 |
| 記録する値 | 平均 FPS、**1パーセンタイル FPS**（下位1%のフレームから求めた値）、フレーム間隔が 33 ms を超えた回数、**最大のフレーム間隔**、1ステップの処理時間の平均と最大、捨てたステップ数（`clockSkip` の合計） |
| 計測の条件 | 実際の試合を、**3試合**行う（標準設定どうし、極端な配分（攻撃8 / 防御2 など）どうし、ヒットが多い試合）。1試合は、最大の90秒まで。**20台を同時に使う条件**でも1回行う（§7.3）。ブラウザの開発者ツールを開かない（影響を避ける）。電源は、AC につなぐ（ノートPCの場合） |
| 計測の場所 | 会場と同じ構成（親機のローカルサーバーから配信し、LANでつなぐ）。HTTP で配信 |
| 繰り返し | 各条件で3回。最悪の回を、結果として採用する |

### 7.3 合格基準

| 項目 | 会場想定PC（必須） | 低性能スマホ（目標） |
|---|---|---|
| 平均 FPS | **58 以上**（60 FPS を維持。画面のリフレッシュレートが 60 Hz のとき） | 50 以上 |
| 1パーセンタイル FPS | **50 以上** | 30 以上 |
| 33 ms を超えるフレームの割合 | **1 % 未満** | 5 % 未満 |
| 最大のフレーム間隔 | **100 ms 未満**（人が気づく止まりがない） | 200 ms 未満 |
| 1ステップの処理時間（最大） | **4 ms 未満**（フレーム予算 16.7 ms の約 1/4。描画の余裕を残す） | 8 ms 未満 |
| 捨てたステップ（`clockSkip`） | **0**（通常の対戦で、1回も捨てない） | 試合時間の 5 % 未満 |
| メモリ | 試合を10回繰り返しても、使用量が増え続けない（§8） | 同左 |
| 描画の品質 | キャラクター・ステージが、崩れずに表示される。HUD の更新が、FPS を下げない | 同左 |

- 基準を満たさないときは、不具合として Issue にし、原因（描画・ステップ処理・GC・HUD の更新）を、計測値から切り分ける。
- 20台を同時に使うときは、**親機のローカルサーバーの負荷**も確認する（20台が、1秒間隔で進行状態を取得する。event-control.md §8.2）。参加者PCの FPS が、サーバーの負荷で下がらないこと。

### 7.4 入力の遅延と同時押し

| 項目 | 方法 | 合格基準 |
|---|---|---|
| 操作の遅延 | 60 fps の動画（ハイスピードカメラ、またはスマホのスローモーション撮影）で、キーを押した瞬間と、画面の反応のフレームを数える | 押してから、**画面が反応するまで 3 フレーム（約50 ms）以内**（目標。最悪でも 6 フレーム以内）。入力は、次のステップで読む（pc-ui.md §5.5）ので、1ステップ（約17 ms）以内の遅れが含まれる |
| 同時押し（ゴースト入力） | **会場と同じ種類のキーボード**で、1P（A D W F）と2P（テンキー 4 6 8 5）の全組み合わせを、同時に押す。S06 のキー確認画面で、押している全キーが光ること | 通常の遊び方（左右移動 + ジャンプ + 攻撃を、両者が同時）で、**入力が落ちない**。落ちる組み合わせがあれば、配置を見直す（pc-ui.md §9） |
| 短い入力の取りこぼし | 1ステップより短い押下（ラッチ）を、自動入力で再現 | すべて、次のステップで、1回の入力として受け取られる（C のテストと同じ。実機でも1回確認） |

### 7.5 体験の時間と分かりやすさ（観察）

| 項目 | 方法 | 合格基準 |
|---|---|---|
| 1ターンの時間 | 初見の中学生役（またはそれに近い人）に、短い説明（event-operation.md §6.1 の台本）のあと、S01 から S12 まで通してもらい、時間を測る | 約20分に収まる。画面ごとの目安（user-flow.md §7）と比べて、大きく超える画面を記録する |
| 1試合の時間 | 試合の開始から END まで | 約2分に収まる（90秒 + READY・END） |
| カスタマイズの時間 | S02 の開始から「つぎへ」まで | 30〜60秒 |
| 迷いやすい場所 | 観察して、止まった・聞き返した画面を記録する | 記録を、文言・画面の改善の材料にする（合否ではなく、改善の入力） |
| 検証エラー・Battle Report・比較の理解 | 説明のあとに、「何が変わって、何が起きたか」を、口頭で言ってもらう | 結果と、能力値の変更の関係に、気づける。正解を示すことばになっていない |

- 観察は、2〜3人以上で行う。リハーサル（#52）と、同じ機会にまとめてもよい。

- PR のたびに、`tsc -b`、`eslint`、`prettier --check`、`vitest run` を実行する。**失敗したら、マージできない**（#40 の完了条件。ブランチ保護の設定は、リポジトリの管理者が行う）。

## 11. 例外・制約

- 会場想定PC の実際の仕様は、現時点で未確認。#51 で記録し、§7.1 と §7.3 の基準を、必要なら見直す（見直したら、変更履歴に記録）。
- 実機の確認は、会場のPC・キーボードが手に入ってからになる。それまで、同種のPCが無いときは、近い性能のPC・100%キーボードで代用し、**代用したことを記録に明記する**（会場の機材で再確認するまで、合格にしない）。
- 自動の画面操作（E2E）は導入しない（§5.5）。手動のチェックが多いため、**チェックの記録を残す**ことで、再現性を保つ。
- 性能の基準値（§7.3）は、暫定。会場想定PCの計測結果と、体感を見て、#51 で確定する。
- ネットワーク対戦は取り下げ済み（REQ-NET-02）のため、通信対戦の同期・遅延の試験は含めない。将来、要求が戻ったときに追加する。
