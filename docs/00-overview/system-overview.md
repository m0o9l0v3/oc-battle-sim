# スマブラ企画 全体仕様書

- 文書ID: SYS-OVERVIEW
- バージョン: 0.1
- 状態: 承認済みの企画方針を整理した基準仕様
- 対象: Claude Codeによる以降の設計・実装
- 用語: 「スマブラ企画」は企画上の呼称であり、成果物は独自のキャラクター・名称・表現を持つ2D対戦ゲームとする

## 1. 目的と概要

本プロジェクトは、中学生向けオープンキャンパス「プログラミング体験 第2回」で使用するWebアプリケーションである。参加者はファイターの能力値やステージを設計し、対戦結果を観察して設定を改善する。

体験の中心はゲームを遊ぶことだけではなく、参加者が設定した値によってシステムの挙動が変化し、その結果をもとに改善することである。

```text
Design → Test → Evaluate → Improve
```

特定のプログラミング言語の文法習得は目的としない。

## 2. 目標と対象ユーザー

### 2.1 目標

- 数値・パラメータとプログラムの動作の関係を直感的に体験できる。
- 設定を変えると結果が変わることを観察できる。
- ポイント制を通して設計上のトレードオフを理解できる。
- 実行結果から改善点を考え、再設計・再戦できる。
- 唯一の正解を押しつけず、参加者自身に判断を委ねる。

### 2.2 対象ユーザー

| 利用者 | 主な利用方法 |
|---|---|
| 中学生 | PCでファイター作成、能力設定、ステージ作成、テスト、対戦、結果評価、再設計を行う |
| 保護者 | スマートフォンからQRコードで対戦ルームに参加し、主に対戦プレイヤーとして利用する |
| スタッフ・学生ヘルパー | オープンキャンパス当日の案内と進行を補助する。親機から参加者端末の進行を管理する |

## 3. 基本体験フロー

```text
開始
  ↓
ファイター作成・能力値設定
  ↓
ステージ作成
  ↓
操作確認・テスト
  ↓
対戦ルーム作成・QRコード表示
  ↓
保護者がスマートフォンで参加（任意）
  ↓
第1戦
  ↓
Battle Report
  ↓
設定の再設計
  ↓
第2戦
  ↓
結果比較・終了
```

**必須の学習サイクル:** 設定 → 対戦 → 評価 → 変更 → 再戦。

## 4. 要求事項

各要求の詳細な受入条件は分野別仕様で定義する。以下の優先度はMVPの範囲を示す。

| ID | 優先度 | 要求 |
|---|---|---|
| REQ-EXP-01 | 必須 | 参加者がファイターの能力値を設定し、設定内容を画面で確認できること |
| REQ-EXP-02 | 必須 | 設定値の違いが対応するゲーム内の挙動に反映されること |
| REQ-EXP-03 | 必須 | 1対1の対戦を行い、勝敗と対戦結果を確認できること |
| REQ-EXP-04 | 必須 | 第1戦後に設定を変更し、再戦できること |
| REQ-EXP-05 | 必須 | 第1戦と第2戦の設定および結果を比較できること |
| REQ-FTR-01 | 必須 | 全員共通の基礎性能と共通の基本操作・攻撃方式を持つこと。性能差は設定したパラメータによって生じること |
| REQ-FTR-02 | 必須 | 4つの能力値 `attackPower`、`defense`、`jumpPower`、`speed` を扱うこと |
| REQ-FTR-03 | 必須 | ファイターの外観はオリジナルの2Dキャラクターとし、円・四角などの図形を貼り合わせただけの表現を避けること |
| REQ-FTR-04 | 必須 | 少数の再利用可能なパーツを組み合わせ、パーツの移動・回転・拡大縮小で簡易アニメーションを表現すること |
| REQ-FTR-05 | 必須 | 能力値による外観変化を設ける場合、視覚的なフィードバックに限り、当たり判定を変えないこと |
| REQ-FTR-06 | 必須 | 短時間で自分のキャラクターだと認識できるカスタマイズを提供すること。キャラ作成だけを主体験にしないこと |
| REQ-STG-01 | 必須 | 対戦用ステージを作成または選択できること。ステージの制約と検証条件は分野別仕様で定めること |
| REQ-CMB-01 | 必須 | 1対1の2D対戦を基本とし、ダメージ蓄積から吹き飛ばし、場外、撃墜につながる勝敗方式を採用すること |
| REQ-RPT-01 | 必須 | Battle Reportに勝敗だけでなく、対戦内容を振り返るための指標を表示すること |
| REQ-RPT-02 | 必須 | 各戦のCharacterConfigを保存し、第1戦と再戦の比較に利用すること |
| REQ-NET-01 | 目標 | PCで対戦ルームを作成し、QRコードからスマートフォンで参加できること |
| REQ-NET-02 | 目標 | ブラウザ間のリアルタイム対戦を提供し、参加者にネットワーク設定を要求しないこと |
| REQ-SHR-01 | 目標 | 当日の対戦ルーム参加用とは別の持ち帰り用QRコードから、イベント終了後も参加者の設定（ファイター・ステージ）を復元し、家庭のPCで遊べること。会期後はバックエンドを必要とせず、GitHub Pagesのみで動作すること |
| REQ-OPS-01 | 必須 | オープンキャンパス会場で短時間に説明・操作でき、当日の安定運用を優先すること |
| REQ-OPS-02 | 必須 | 進行を管理する親機から、再戦の受付停止・終了の指示・リセットなど、参加者端末の進行を管理できること。再戦は何度でもできるが、1ターン約20分に収める。親機と通信できなくても、参加者の体験が止まらないこと |

## 5. ファイターと能力値の基準

### 5.1 能力値の意味

| 設定項目 | 参加者向けの意味 | 主に影響する挙動 |
|---|---|---|
| `attackPower` | 攻撃力 | 1回の攻撃で与えるダメージ |
| `defense` | ふっとばされにくさ | 攻撃を受けた際の吹き飛ばされやすさ |
| `jumpPower` | ジャンプ力 | ジャンプ高度 |
| `speed` | 移動速度 | 横方向の移動速度 |

各能力値は、できる限り対応する一つの現象に影響させる。具体的な計算式、係数、調整値は戦闘・ファイター分野別仕様で定義する。

### 5.2 ポイント制

```text
最小値: 2
最大値: 8
合計ポイント: 20
標準設定: Attack 5 / Defense 5 / Jump 5 / Speed 5
```

対戦開始には全ポイントを使用する。能力値の追加ペナルティはMVPでは設けず、合計ポイント制でトレードオフを表現する。標準設定は4項目の合計が20となる。

### 5.3 外観とカスタマイズ

キャラクターはオリジナルの2Dデザインとする。パーツ構成の想定は頭、胴体、左右の腕・脚、顔、アクセサリー。Idle、Run、Jump、Fall、Attack、Hit、KO程度の状態を簡易アニメーションで表現する。

Body、Face、Color、Accessory、Character Nameなどの選択肢を候補とする。カスタマイズ操作の目標時間は30〜60秒程度。能力値の特徴を外観にも反映する場合は、小さな視覚差にとどめ、対戦上の当たり判定には影響させない。

## 6. 対戦・ステージ・結果の基本方針

### 6.1 対戦

- 形式は1対1を基本とする。
- MVPでは全プレイヤーに同じ基本攻撃方式を適用する。
- 基本の勝敗モデルは「ダメージ蓄積 → 吹き飛び量増加 → ステージ外 → 撃墜」とする。
- ダメージ式、吹き飛ばし式、防御補正、ストック数、試合時間などは `03-combat` 配下で定義する。
- PCの最低限の操作は左右移動、ジャンプ、攻撃。スマートフォンは画面上の仮想コントローラーを使う横持ちを基本候補とする。

### 6.2 ステージ

前回の `oc26-stage` 資産は再利用候補として調査する。グリッドエディタとCanvasゲームの構成を候補とし、対戦が成立するための床面積、高度、足場間隔、スポーン領域、場外領域などの制約を設ける。詳細なデータ形式、制約、検証方法は `04-stage` 配下で定義する。

### 6.3 Battle Reportと比較

Battle Reportは企画の主要機能であり、単なる勝敗表示にしない。指標候補は与ダメージ、被ダメージ、撃墜数、撃墜された数、耐えた最大ダメージ、復帰成功・失敗など。記録する指標は詳細仕様で絞り込む。

第1戦と第2戦について、設定値、変更点、結果を比較可能にする。システムは結果と判断材料を提示し、改善方法を一つの正解として指示しない。

## 7. MVP

MVPでは次の一連の体験を完了できることを必須とする。

```text
ファイター作成・能力設定
  → ステージ
  → 1対1対戦
  → Battle Report
  → ファイター設定変更
  → 再戦
  → 結果比較
```

ネットワーク対戦はローカル対戦と切り分けて開発できる設計にする。QRコードによるスマートフォン参加・親子対戦は目標機能であり、全体の学習サイクルが損なわれない段階的な実装単位とする。親機による進行管理（REQ-OPS-02）はMVPに含める。親機と参加者端末の通信は、ネットワーク対戦（REQ-NET）とは独立して動作する設計にする。持ち帰り（REQ-SHR-01）はMVPには含めず、ローカル対戦が成立した後の目標機能とする。

### 7.1 MVPに含めない機能

- 多数の固有キャラクターやキャラクター固有技
- 複雑なコンボシステム、アイテム、4人対戦
- ランキング、アカウント登録、永続プロフィール、課金
- 3Dキャラクター、高度な物理エンジン
- 高度なCPU AI

## 8. 非機能要件

| ID | 要件 |
|---|---|
| NFR-01 安定性 | オープンキャンパス当日の安定動作を最優先する。過剰な機能より、迷わず完了できる体験を優先する |
| NFR-02 分かりやすさ | 中学生が短い説明で利用できること。操作や用語を増やしすぎない |
| NFR-03 応答性 | 対戦中の目標は60 FPS。明確な操作遅延を感じさせない。低性能スマートフォンも考慮する |
| NFR-04 デバイス | PCのデスクトップブラウザを主端末とする。親子対戦用スマートフォンはiOS Safari、Android Chromeを主対象とする |
| NFR-05 視覚品質 | キャラクターは没入感に関わるため、記号的な図形の貼り合わせに留めず、オリジナルキャラクターとして認識できる水準を確保する |
| NFR-06 表現方式 | 3Dを原則使わず、Canvas 2Dを中心にする |
| NFR-07 独自性・権利 | Nintendoのキャラクター、画像、UI素材、BGM、効果音、ロゴ、ステージ素材を使用しない。キャラクター、UI、世界観はオリジナルとする |
| NFR-08 運用性 | フロントエンドはGitHub Pagesを第一候補とし、GitHub Actionsでビルド・配置する。GitHub Pagesは、イベント終了後に持ち帰ったQRコードから、体験中に作成したステージ・設定に接続するためのホスティング先とする（REQ-SHR-01）。会場の有線LANはインターネットに出られないため、イベント当日のアプリの配信、進行管理、リアルタイム通信は、会場LAN内の親機PCのローカルサーバーが担当する（`08-architecture/event-connection.md`） |

## 9. 技術・構成の初期候補

前回資産との互換性を考慮し、現時点の候補を以下とする。具体的な採否と実装構成は `08-architecture` 配下で決定する。

- フロントエンド: TypeScript、React、Vite
- 描画: Canvas 2D
- ホスティング: GitHub Pages（フロントエンドの第一候補。イベント終了後の持ち帰り用QRからの接続先）
- リアルタイム通信: 会場LAN内の親機PCのローカルサーバー（WebSocket）。スマホ参加は、インターネットにつながない自前のWi-Fiルーター経由。状態同期または入力同期、権威モデル、再接続を比較検討
- 論理モジュール候補: ゲームエンジン、物理、戦闘、ステージ、バトル、ファイター設定・描画・アニメーション、各種エディタ、通信、レポート、UI、アセット

前回の `oc26-stage` からは、Canvas描画、ゲームループ、衝突判定、グリッドエディタ、ステージデータ、QRコード生成、URLデータ共有、モバイル入力、UIなどを候補として調査する。各資産は `Reuse`、`Refactor`、`Replace`、`Discard` の観点で評価し、無条件に流用しない。

## 10. 設計原則

1. ゲームの規模より、体験目的を優先する。
2. 一つの設定変更と一つの観察可能な現象を結び付ける。
3. 参加者に唯一の正解を押しつけない。
4. 対戦を一度で終わらせず、振り返りと再戦につなげる。
5. 当日の安定性を機能数や実装の凝り具合より優先する。
6. 短時間で理解できない機能や複雑な操作を避ける。
7. ファイターの視覚的完成度を大切にしつつ、大量の固有モーション制作は避ける。
8. 「スマブラ風」は参考概念に留め、知的財産と誤認を招かない独自表現にする。
