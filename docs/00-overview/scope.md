# スコープ定義（scope.md）

- 文書ID: OVW-SCOPE
- バージョン: 0.1
- 状態: 草案
- 上位文書: [system-overview.md](./system-overview.md)（§4、§7）

## 1. 概要

system-overview.md の要求を、**MVP（必須）**、**目標機能**、**対象外**に分け、実装のマイルストーンと対応付ける。範囲に迷ったときの判断基準とする。

## 2. 目的

- 「何を作り、何を作らないか」を一箇所で確認できるようにする。
- 要求の優先度（必須 / 目標）を、マイルストーンと Issue に結びつける。
- 範囲の変更を暗黙に行わず、変更履歴に残す。

## 3. 範囲の区分

| 区分 | 意味 | マイルストーン |
|---|---|---|
| **MVP** | 完了しなければならない。これが欠けると企画の体験が成立しない | M0〜M2、M4 |
| **目標機能** | 実装を目指すが、MVPの完成を妨げない。ローカル対戦の成立後に取り組む | M3 |
| **対象外** | 今回は作らない | — |

マイルストーンの内容は次のとおり。

| マイルストーン | 内容 |
|---|---|
| M0 基盤・調査 | リポジトリ雛形、文書構成、前回資産の評価 |
| M1 分野別仕様 | 全体仕様を分野別仕様・受入条件へ詳細化する |
| M2 MVP ローカル学習サイクル | PC1台で「作成→ステージ→対戦→Report→再設計→再戦→比較」を完了できる |
| M3 スマホ参加・オンライン対戦 | QRコードでスマートフォンが参加し、ブラウザ間で対戦できる。持ち帰り用QRを含む |
| M4 当日運用準備 | 実機検証、権利確認、当日チェックリストとリハーサル |

## 4. MVPの必須体験

MVPでは、次の一連の体験をPC上で完了できることを必須とする（system-overview.md §7）。

```text
ファイター作成・能力設定
  → ステージ
  → 1対1対戦
  → Battle Report
  → ファイター設定変更
  → 再戦
  → 結果比較
```

- 対戦はPC1台でのローカル2人対戦とする。ネットワーク対戦は含めない。
- 進行を管理する親機（REQ-OPS-02）はMVPに含める。親機と参加者端末の通信は、ネットワーク対戦とは独立して動作する。
- ネットワーク対戦は、ローカル対戦と切り分けて開発できる設計にする。

## 6. 対象外の機能

system-overview.md §7.1 に基づき、次の機能はMVPに含めない。

- 多数の固有キャラクターや、キャラクター固有技
- 複雑なコンボシステム、アイテム、4人対戦
- ランキング、アカウント登録、永続プロフィール、課金
- 3Dキャラクター、高度な物理エンジン
- 高度なCPU AI

あわせて、次の点も対象外として扱う（`oc26-stage` からの取り込み判断。[legacy-assessment.md](../08-architecture/legacy-assessment.md)）。

- 敵・トゲ・ジャンプ台・落ちるブロックなど、1人用ステージのギミック
- 印刷機能（持ち帰り用QRコードを紙で配布する場合に見直す）
- 学校ロゴは、許可の範囲（オープンキャンパスでの使用）を超えて使わない

## 7. 範囲の判断基準

範囲に迷う機能は、次の順に確認する。

1. 学習サイクル（設定→対戦→評価→変更→再戦）の完了に必要か。必要ならMVP。
2. 当日の安定性を損なわないか（設計原則 5）。損なうなら入れない、または後回しにする。
3. 短時間で理解できるか（設計原則 6）。複雑になるなら入れない。
4. 上記を満たさず、あれば体験が良くなるだけなら、目標機能または対象外にする。

## 8. 範囲の変更

範囲の変更（MVPの追加、目標機能のMVP化、対象外の取り込みなど）は、暗黙に行わない。次の手順で行う。

1. 変更の理由と影響を、本書の変更履歴に記録する。
2. 上位方針が変わる場合は、system-overview.md も更新する。
3. 影響を受ける Issue のマイルストーンとラベルを更新する。
